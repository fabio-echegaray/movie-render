3. PERFORMANCE
──────────────

  [OPEN] 29. MovieRender saves every frame to disk then re-reads it
              (`_sequential.py:260,130`) — the frame data is already a numpy
              array; capturing it in memory would eliminate the I/O round-trip.
              Fix: compare `frame_count × frame_bytes` against available
              system memory. If it fits, keep rendered frames in a list and
              feed them directly to moviepy. Otherwise, fall back to the
              current disk path. Available memory can be read via
              `psutil.virtual_memory().available` or `os.sysconf`.

  [OPEN] 72. Apparent memory leak in z-projection for large files
              — When rendering panels/movies with large OME-TIFFs
              (many z-slices × frames × channels), RSS grows steadily and
              is not reclaimed after each subplot. Three likely sources:
                (a) `_zprj_populate_state()` (`_shared_zproj_state_mixin.py:50`)
                    eagerly enqueues a z-projection for *every*
                    frame×channel combination at first access; the background
                    `_zproject()` thread then materialises full-resolution
                    MetadataImages (numpy arrays) and keeps up to 20 of them
                    simultaneously in the shared `_zcache_state` dict (the
                    `imgs_done ≥ 20` throttle at line 198). Even after the
                    consumer sets `ckeyelem['image'] = None`, the dict entry
                    itself (with all its scalar fields) is never evicted.
                (b) `CompositeRGBImage.__call__` (`_image_pipeline_composite_rgb.py:55`)
                    allocates a fresh `np.zeros((H, W, 3), dtype=np.float64)`
                    per subplot (~96 MiB for 2048×2048). Matplotlib retains
                    the rendered image data in the `Axes` until the figure is
                    explicitly closed or garbage-collected; the panel loop
                    never calls `plt.close()`, so figures accumulate for the
                    entire render pass.
                (c) The `fileops` ImageFile instances (and their cached
                    metadata / processor lists) outlive the render loop
                    because the panel reader holds references via
                    `ConfigPanel.image_file`.
              — Explore: (1) evict `_zcache_state` entries once all keys
              reach `state == 'used'`; (2) close each panel figure after
              `pdf.savefig()` in `render_static_montage`; (3) profile RSS
              before/after (b) to quantify the gain before tackling (a)/(c).


4. UX
──────

  [DONE] 47. Graceful early termination in `render_folder_cmd` (`_render_folder.py:34`)
               — When rendering a folder of config files, the user should be
               able to press Ctrl-C once to finish the current movie and stop
               (no further movies), or press Ctrl-C twice to terminate
               immediately. Currently, any KeyboardInterrupt kills the entire
               batch mid-render.
               Fix: two-phase SIGINT handler in `_render_folder.py`:
               first Ctrl-C sets `fileops.__STOP_REQUESTED` and replaces
               handler; current render finishes normally, folder loop checks
               `__STOP_REQUESTED` after each render and breaks. Second Ctrl-C
               sets `fileops.__THREAD_STOP_REQUESTED` (tells z-projection
               background thread to stop) and raises `KeyboardInterrupt` for
               immediate termination. `_base_composer.py` no longer catches
               KeyboardInterrupt in the sequential path (unnecessary — first
               press doesn't raise one, second press propagates through).

  [DONE] 47b. Z-projection hang on Ctrl-C (`_base_composer.py:212`)
               — First implementation of point 47 caused z-projection
               background threads to hang the system. Pressing Ctrl-C stopped
               all z-projection threads mid-computation, leaving the main
               render loop waiting for images that would never arrive.
               Fix: two-event approach — `__STOP_REQUESTED` for the folder
               loop (first Ctrl-C), `__THREAD_STOP_REQUESTED` for background
               threads (second Ctrl-C / SIGTERM). Background thread checks
               `__THREAD_STOP_REQUESTED` and exits when set.
               FileOps: removed SystemExit from _zproject() except clause
               so second Ctrl-C terminates threads immediately.
               FileOps: `__IS_EXITING` renamed to `__THREAD_STOP_REQUESTED`.

  [DONE] 51. Project-folder-level configuration with section-level overrides

  [DONE] 52. Render commands access media files excessively before rendering
              — Profiled the render flow: `read_config()` opened/read the
              media file once for projections (DATA section) and then AGAIN
              inside every header-reader plugin that lazily loaded its own
              data section (`HeaderReaderPlugin._img_file`/`_param_override`).
              A movie-only config caused 2 media loads; adding ROI or arrow
              overlay sections raised it to 3-4 loads per config file.
              — FileOps fix (imgfileops, see FileOps TODO #19):
                * `HeaderReaderPlugin.__init__` accepts pre-loaded
                  `cfg`/`img_file`/`param_override`/`roi` (seeded via a
                  sentinel so a legitimate `roi=None` is still honored);
                  `_load_data_section()` only fills slots that were not
                  provided.
                * `read_config()` and `check_if_output_files_are_created()`
                  pass their already-loaded objects into the plugins.
              — MovieRender fix (call patterns):
                * `load_overlay_plugins()` and the nested ROI/OVERLAY
                  plugin instantiation in `_movie_header_reader.py` (and
                  the panel reader) propagate the shared data-section
                  objects, so overlay/ROI readers reuse the loaded
                  `img_file` instead of re-opening the file.
                * `.info` for a shared `image_file` is computed once per
                  config file (`_render_configfile.py`, `_render_movie.py`,
                  `_render_projection.py`), removing repeated stat() calls
                  when several sections point at the same file.
              — Result: exactly one media-file load per config file.

  [DONE] 62. Auto-detection of defaults.cfg does not search upstream directories
               — Previously, `render folder` auto-detected `defaults.cfg` only
               in the root `path` argument, and individual commands (`render file`,
               `render movie`, `render panel`, `render projection`) only checked
               CWD. When config files live in subdirectories and `defaults.cfg`
               is at a parent directory, the search missed it.
               Fix: all commands now search for `defaults.cfg` from the config
               file's directory up to CWD, then up to filesystem root. Found
               files are combined (closest to config file = highest priority).
               Individual commands accept `--defaults-file` to override.
               Implementation: `find_defaults_files()` in `_defaults.py` used
               by all entry points. `defaults_file` type changed from
               `Path | None` to `Path | list[Path] | None` across FileOps
               (`read_config`, `check_if_output_files_are_created`,
               `read_data_section`, `update_overrides_from_channel_sections`,
               `HeaderReaderPlugin`).
               — Additionally, `savefig(facecolor='white')` in
               `_sequential.py` was overriding the configured background
               color. Fixed to use `self._cfg.background.color`.

  [DONE] 63. `fontdict` + `fontsize` alias conflict crashes rendering

  [OPEN] 64. Depth-coded z-projection for PANELs and MOVIEs
