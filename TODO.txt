1. CRITICAL BUGS
────────────────

  [OPEN]  1. `parallel | True` always forces parallel (`_render_movie.py:37`)
               — `|` is bitwise OR (`True | False` = 1), so every movie
               renders in parallel mode regardless of the flag. Comment says
               "remove True value set for debugging". This is the gate that
               forces all renders into the broken parallel path.
               Fix: change `parallel | True` to just `parallel`.

  [OPEN] 54. Temp directory not cleaned up on exception (`_sequential.py:207`)
              — `shutil.rmtree(self._tmp)` not in `try/finally` block.
              If `write_videofile()` raises, the temp dir is orphaned.
              Fix: wrap cleanup in `try/finally`.

  [OPEN] 75. Unmatched panel/movie overlays are dropped silently
              (`_panel_header_reader.py:95`, `_movie_header_reader.py:155`)
              — a panel's `overlays = [wall_001]` whose id matches no loaded
              overlay plugin is removed by the
              `[ovr for ovr in overlays if ovr.overlay_id in ovr_ids]` filter
              with no log message and no error — the rendered movie silently
              misses the requested content.
              Fix: log a warning (or raise) for every requested id with no
              matching plugin, in both the panel and movie readers.

  [OPEN] 76. Parallel rendering exhausts memory and freezes the computer
              (`_base_composer.py:125`, gated from `_render_movie.py:37`)
              — Movies always hit the parallel path because of bug #1
              (`parallel | True` in `_render_movie.py:37` forces
              `_render_parallel()` regardless of the flag). For a large
              SoRA .nd2 (multi-GB, often 100+ GB with multiple positions)
              this multiplies memory and thrashes the host:
                (a) `_render_parallel()` materialises a `composer_array` of
                `n_workers + 1` full composer copies in the parent
                (`_base_composer.py:131-177`), each holding a complete
                fileops `ImageFile` (metadata, processors, cached planes),
                with `n_workers = os.cpu_count()` — that alone is tens of GB
                of heap before any frame renders.
                (b) `futures.ProcessPoolExecutor(max_workers=os.cpu_count(),
                initializer=...)` (`_base_composer.py:185`) forks one worker
                per CPU. Each worker faults the .nd2's memory-mapped pages
                into its OWN RSS as it renders its frames, so total RSS ≈
                n_workers × file-bytes-touched + the parent copy — a
                126 GB rab5.nd2-style file on a 24-core machine demands
                hundreds of GB and swaps/OOMs the system (the "freezes the
                computer" report).
                (c) Every `executor.submit(run_job, composer, fr, ...)`
                (`_base_composer.py:191`) pickles the entire composer +
                `ConfigMovie` + `ImageFile` on each of the n_frames
                submissions.
                (d) The shared z-cache is duplicated across workers:
                `run_job()` calls `imf.init_shared(...)` per frame
                (`_base_composer.py:241`), so each worker spawns its own
                `_zproject()` background thread recomputing the same
                frame×channel projections against ONE shared `Manager` dict
                (see FileOps #12 / MovieRender #72).
              Replicate: render any multi-GB (ideally multi-position) movie
              with the current code — `movierender render movie` or
              `render folder` on a real SoRA .nd2 — and watch RSS climb to
              many times the file size before the render finishes or the
              machine thrashes.
              Fix: (1) fix #1 first — pass `parallel=parallel` instead of
              `parallel | True` so renders stay sequential by default. (2) If
              the parallel path is kept: stop holding `n_workers+1` composers
              in the parent (submit cheap per-frame payloads that re-open the
              image lazily in the worker), cap `n_workers` well below
              `os.cpu_count()`, start workers with 'spawn' so they do not
              fork a huge parent, and give each worker its own local (non-
              shared) z-cache. (3) Add an RSS guard that falls back to the
              sequential path when the product of file size × `n_workers`
              exceeds available memory.

3. PERFORMANCE
──────────────

  [OPEN] 29. MovieRender saves every frame to disk then re-reads it
              (`_sequential.py:260,130`) — the frame data is already a numpy
              array; capturing it in memory would eliminate the I/O round-trip.
              Fix: compare `frame_count × frame_bytes` against available
              system memory. If it fits, keep rendered frames in a list and
              feed them directly to moviepy. Otherwise, fall back to the
              current disk path. Available memory can be read via
              `psutil.virtual_memory().available` or `os.sysconf`.

  [OPEN] 72. Apparent memory leak in z-projection for large files
              — When rendering panels/movies with large OME-TIFFs
              (many z-slices × frames × channels), RSS grows steadily and
              is not reclaimed after each subplot. Three likely sources:
                (a) `_zprj_populate_state()` (`_shared_zproj_state_mixin.py:50`)
                    eagerly enqueues a z-projection for *every*
                    frame×channel combination at first access; the background
                    `_zproject()` thread then materialises full-resolution
                    MetadataImages (numpy arrays) and keeps up to 20 of them
                    simultaneously in the shared `_zcache_state` dict (the
                    `imgs_done ≥ 20` throttle at line 198). Even after the
                    consumer sets `ckeyelem['image'] = None`, the dict entry
                    itself (with all its scalar fields) is never evicted.
                (b) `CompositeRGBImage.__call__` (`_image_pipeline_composite_rgb.py:55`)
                    allocates a fresh `np.zeros((H, W, 3), dtype=np.float64)`
                    per subplot (~96 MiB for 2048×2048). Matplotlib retains
                    the rendered image data in the `Axes` until the figure is
                    explicitly closed or garbage-collected; the panel loop
                    never calls `plt.close()`, so figures accumulate for the
                    entire render pass.
              — Partially addressed: figures are now closed after each panel
                (`layouts/panel/_main.py`, both multipage and single-page
                branches) and after each movie composer render
                (`layouts/_base_composer.py render()`, finally block reuses
                the pattern from run_job). zcache (a) is only hit for
                n_zstacks > 1 files and is still open.
                (c) The `fileops` ImageFile instances (and their cached
                    metadata / processor lists) outlive the render loop
                    because the panel reader holds references via
                    `ConfigPanel.image_file`.
              — Explore: (1) evict `_zcache_state` entries once all keys
              reach `state == 'used'`; (2) close each panel figure after
              `pdf.savefig()` in `render_static_montage`; (3) profile RSS
              before/after (b) to quantify the gain before tackling (a)/(c).

  [OPEN] 61. Channel name overlay with color indicator
              — Add an overlay that displays the channel name preceded by a
              small colored square (the size of a character) representing the
              channel color. Configurable parameters: position, point size (for
              both font and square), font name, and font properties.

  [OPEN] 64. Depth-coded z-projection for PANELs and MOVIEs
              — Add a new z-projection mode that maps each z-slice to a
              color along a colormap (e.g. blue→red, jet, etc.), producing
              a 2D image where pixel color encodes the z-position of peak
              intensity. This is Fiji's "Temporal-Color Code" macro:
              https://github.com/fiji/fiji/blob/master/plugins/Scripts/
              Image/Hyperstacks/Temporal-Color_Code.ijm
              Reference: https://github.com/napari/napari/issues/4300
              — Configurable parameters: colormap name (default: hsv or
                jet), z-range (full or subset), intensity threshold.
              — Should work for both individual MOVIE sections and PANEL
                layouts, and compose with existing overlays.
              — Implementation: new z-project mode in fileops (or a
                MovieRender plugin) that assigns each z-slice an index,
                maps index to a colormap color, and composites the
                result per-pixel by taking the color at each position's
                maximum-intensity z.

  [BUG] 69. `timestamp_color` / `timestamp_font_size` ignored in configs
                — Panel (`figs/definitions/chx-2003/panel/export_definition.cfg`)
                sets `timestamp_color = white`, `timestamp_font_size = 10`,
                but `_parse_text_props(cfg_section, 'timestamp')` only reads
                the dotted keys `timestamp.color` / `timestamp.font_size`.
                `timestamp_color`/`timestamp_font_size` are different keys to
                configparser, so the parser silently returned the defaults
                (`TextProperties(font_name='Arial', font_size=12, color=None)`)
                and the rendered timestamp ignored the configured colour/size.
                — Fix: `_get_prefixed_key()` falls back from the dotted form
                to the underscore form for `_parse_text_props`,
                `_parse_line_props` and `_parse_background_props`, so both
                syntaxes work (`timestamp.color` or `timestamp_color`, etc.).
                — Regression tests in `test/test_config_graphics.py`.
